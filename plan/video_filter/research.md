# video_filter 执行效率与并发不足排查

> 日期：2026-10-06。本文覆盖原 research.md。
>
> 本文保留编码前的日志、配置与代码诊断基线。后续 P0—P8 已进入代码实施，见 [performance-implementation.md](performance-implementation.md)；基线数据不代表新版性能。

## 1. 结论

当前并发排不满、任务之间有间隔，主要来自任务发现与资源准入机制，并非把线程数提高就能解决：

1. **显存准入公式限制并发。** RTX 3060 Ti 为 8GiB，但第 4 个共享任务要求当时仍有 8GiB 空闲显存，第 6 个要求 12GiB；当前规则无法达到配置的 6 个共享任务。
2. **等待中的任务阻止后续任务发现。** 一个预测或分类任务因资源不足留在 queued 后，每轮都会被重新找到；去重返回同一个 queued 任务，发现函数立即返回，后面的预测和提取任务没有机会入队。
3. **每组每轮最多启动一个任务。** 控制轮次每 2 秒执行一次，启动首个任务后就 break，无法一轮补齐空槽。
4. **预测、提取和分类搬运共用 GPU 名额。** 分类在 CPU 文件复制及多轮哈希期间仍占着名额，预测也被套用提取任务的显存门槛。
5. **控制路径反复校验全部模型权重。** 一次需要对约 513MiB 本地文件计算 SHA-256；任务发现、登记和执行都会重复执行。
6. **初始扫描存在明显耗时。** 本次首轮对账耗时 376.8 秒，新登记的视频直到整轮提交后才对执行队列可见。

下一阶段采用已确定的显存准入条件：**当前空闲显存 >= 新任务预计增加的显存峰值 + 安全余量**。落地阶段与验证要求见 [codingplan.md](codingplan.md)。

这些机制叠加后形成“少量提取 → 等预测 → 等搬运/对账 → 再少量提取”的节奏。现有日志缺少准入拒绝原因和阶段细分计时，不能把每一秒停顿精确归因。

## 4. 原因、机制与证据强度

### 4.1 显存准入规则：确定的容量限制

位置：[resources.py](../../automation-server/media_lineage/resources.py) 的 `request_lease()`。

共享任务的准入条件是：

```python
free_memory(device) >= 2048 * (len(active) + 1)
```

| 准备准入的共享任务 | 要求当时的空闲显存 |
| --- | --- |
| 第 1 个 | 2048MiB |
| 第 2 个 | 4096MiB |
| 第 3 个 | 6144MiB |
| 第 4 个 | 8192MiB |
| 第 6 个 | 12288MiB |

`free_memory` 已经扣除了运行中任务的实际占用，再按全部任务数量乘以 2GiB 预留，导致准入越来越严格。第 4 个任务在本机实际空闲显存上限约 8024MiB 时就无法准入；正在运行的任务占用显存后，第 3 个也可能被拒绝。

预测与 classify 只要包含 MIL，同样申请 `extract_shared`。所以这里限制的是提取、MIL 预测和相关分类任务的合计，而不是给提取保留 6 个专属名额。

日志没有 OOM 降并发记录。现有公式已能解释无法达到 6 个的情况，不能把并发不足直接归因于 OOM。

提取日志中的 PyTorch 单进程峰值最大约为 DINO 97.3MiB、VideoMAE 135.4MiB、BEATs 390.9MiB，但该指标不含全部 CUDA 上下文、FFmpeg/NVDEC 占用和其他进程，不能据此保证 6 路一定安全。

#### 4.1.1 已确定的新准入方案

```text
当前空闲显存 >= 新任务预计增加的显存峰值 + 安全余量
```

不再将正在运行的任务数量乘以固定 2GiB。当前显存占用约 3GiB、空闲约 5GiB 时，若新任务预算 1GiB、安全余量 1GiB，便满足显存条件；是否启动还须通过最大并发、独占租约和任务有效性检查。

- “新任务峰值”覆盖该任务剩余计算阶段可能增加的显存，包括模型、CUDA 上下文、输入/中间张量和 NVDEC；顺序执行四路特征采用阶段最大值及必要重叠，不简单相加所有模型。
- 提取与 MIL 推理分别估算；仅复制/哈希的搬运阶段不申请 GPU 推理名额。
- 安全余量是每张 GPU 的剩余空间保护，不按运行任务数倍增。预算先使用可配置启动值，再结合驱动级测量与 OOM 记录校准；PyTorch 单进程统计仅作为辅助证据。
- 批量启动存在显存尚未兑现的窗口：已经获得许可但还没加载模型的任务，需要保留其未兑现预算。实现中的“可用于新增准入的空闲显存”应从驱动空闲值扣除这些预留，再应用上述公式；已经实际占用的部分不重复扣除。
- 查询、未兑现预算、准入与租约更新按物理 GPU 在同一短事务锁内处理；不能让六个任务同时用同一份空闲显存作判断。
- 保留配置并发上限 6、独占训练/压缩协调、任务退出释放、进程身份核验和 OOM 降级，不保证所有视频类型下 6 路都是最佳吞吐。

### 4.2 queued 任务让发现过程提前返回：确定的调度缺陷

位置：[runtime.py](../../automation-server/video_filter/runtime.py) 的 `enqueue_automatic()`、`_enqueue_extraction()`，以及 [tasks.py](../../automation-server/video_filter/tasks.py) 的 `enqueue_task()`。

当前发现顺序为训练 → 已有摘要的预测/分类 → 新摘要提取，每段遇到一个 queued 任务就返回：

```text
发现候选视频
  → enqueue_task 去重找到已有 queued 任务
  → 返回这个已有任务
  → enqueue_automatic 看到 queued，立即结束
  → supervisor 准入被拒绝，任务继续 queued
  → 下一轮重复同一条链
```

“本轮新建了任务”和“已有任务仍在等待”没有区分。结果不是重复创建数据库行，而是重复做配置、清单、摘要及任务快照校验，且阻止后面的任务发现。

提取分支自身也存在同样情况：一个较早的 queued 提取任务会阻止后面的提取候选入队。候选查询最多取 20 条，因此后续批量发现还需要排除相同输入的 queued/running 任务，并保留既有失败任务的人工重试语义。

### 4.3 单轮补位只有一个任务：确定的吞吐限制

位置：[supervisor.py](../../automation-server/video_filter/supervisor.py) 的 `tick()` 和 runtime 的 `register_schedules()`。

- 每组调用一次 `enqueue_automatic()`，一般只登记一个候选。
- queued 查询之后，启动第一个可执行任务便 `break`。
- 一轮虽然能检查多个已有 queued 候选的准入，但最多启动其中一个。
- supervisor 固定每 2 秒运行，超时执行会受到 max_instances=1、coalesce 的影响。
- 所有启用组轮询；当前只有一个启用组，因此不是靠其他组填满槽位。

理想条件下从 0 补到 6 个，最后一个至少比第一个晚 5 轮，即约 10 秒；实际还叠加权重校验和资源等待。线程池虽然有 66 个线程，却改变不了这个补位限制。

保持 max_instances=1 有助于避免控制轮次重叠。本问题不宜通过直接提高它来解决，应改成单个短轮次内有界批量补位。

### 4.4 重复预测与搬运期间持有 GPU 名额：确定的资源浪费

位置：[prediction.py](../../automation-server/video_filter/prediction.py) 的 `predict_both()`，以及 [transfer.py](../../automation-server/video_filter/transfer.py) 的 `classify()`、`advance_transfer()`。

当前先执行 predict，随后 classify 再调用 `predict_both()`。预测复用查询使用 `prediction_batch_id == 当前 task.id`，两个任务 ID 不同，因此对同一摘要及模型版本仍会重新执行两套预测。

固定日志窗口内 12 个 predict 加 11 个 classify 对应 **23 次 MIL 推理启动、46 条模型预测输出**，与两套模型在这两类任务中都执行相符。MIL 子进程还会为每次调用重新启动并加载模型。

classify 的租约覆盖整个任务：文件读取/哈希 → 推理 → 暂存复制 → 校验 → 发布 → 源清理。该窗口内 classify 总耗时约 6.3—20.0 秒，许多时间属于 CPU 和磁盘工作，却仍占着共享 GPU 名额。

另外，`predict_both()` 会通过 `lock_assets()` 对两套模型训练快照里的全部资产获取排他行锁。相同模型的预测拥有大量共同锁对象，并跨 MIL 推理持有，因此多个预测在 PostgreSQL 中可能串行等待。这是明确的代码串行化因素，但本文没有生产数据库锁等待采样，不能量化它在各次停顿中的占比。

### 4.5 全权重校验处于控制热路径：确定的重复开销

位置：[manifest.py](../../automation-server/video_filter/features/manifest.py) 的 `load_model_manifest()`。

每次调用都读取清单中全部 artifact 文件并计算 SHA-256，没有缓存。只读检查得到：

| 权重 | 大小 MiB |
| --- | --- |
| BEATs | 344.75 |
| DINO | 84.19 |
| VideoMAE | 84.11 |
| eGeMAPS 配置 | 约 0 |
| 合计 | 513.05 |

单次完整校验实测约 **0.464 秒**，没有加载模型或运行推理。该值是一次读取计时，受文件缓存和磁盘状态影响，不是稳定基准。

发现每轮执行一次，`enqueue()` 与 `execute()` 又会执行。仅对照 301 条登记记录，就可看到数百次重复校验路径，另有每轮发现和任务执行的开销。文件缓存可能减少物理磁盘读取，但仍重复读取缓存数据并计算哈希。

### 4.6 扫描、稳定期和血缘对账：应保留的保护，也有可优化部分

位置：[tracking.py](../../automation-server/video_filter/tracking.py) 的 `reconcile()`，以及 supervisor 的 `_scan_group()`。

初始扫描会串行处理全部观察项，新登记结果等到整轮提交才可被执行队列读取。逐文件读取配置、查询 Observation/Location、flush、全文件哈希等均在这条路径内。已有位置且元数据未变的文件会复用哈希，因此后续扫描明显快于首轮。

用户移动及程序搬运会触发目录通知，新位置也会经历 stable_seconds；尚未消费的相关血缘事件会让 `reconciliation_pending()` 暂停自动发现。固定窗口有 47 条“血缘尚待扫描对账”等待记录。扫描完成耗时通常为数秒，但与资源和任务发现等待叠加后，会扩大任务间隔。

这些保护避免将移动或压缩中途消失的视频误判为用户删除。优化不能直接移除稳定期、跳过血缘核验，或把未完成扫描当成删除证据。

### 4.7 单视频内部：进程启动、反复解码和文件读取

位置：[extraction.py](../../automation-server/video_filter/extraction.py)、[media.py](../../automation-server/video_filter/media.py)、[worker_client.py](../../automation-server/video_filter/worker_client.py)。

有音轨时，每个 10 秒窗口通常启动 6 次 FFmpeg：DINO 3 次单帧、VideoMAE 1 次连续片段、BEATs 1 次音频、eGeMAPS 再解码同窗口音频 1 次。287 个窗口对应约 1722 次调用；这是代码路径推导，未通过进程监控逐次计数。

视频确实使用 NVDEC，但每次调用仍有进程及 CUDA 解码上下文初始化，帧还会进入主机内存做 RGB 缩放/裁剪、预处理，再送入 PyTorch。这不是完全在 GPU 内传递帧的流水线。

每个视频 worker 都顺序加载/卸载四路模型，并进行提取前后全文件哈希；主执行器也有提取前后源核验。这些核验服务于数据一致性，不能简单取消。当前 batch_size=1 只影响 DINO 的局部帧批处理，并未把不同窗口或不同视频组合批推理。

## 5. 建议改造顺序

| 顺序 | 改造 | 目的与约束 |
| --- | --- | --- |
| P0-1 | 将训练、预测/搬运、提取的发现独立执行，批量补足有界队列；跳过已有同输入 queued/running 候选 | 一个等待任务不能阻止其他工作入队；保留去重、组隔离及失败重试边界 |
| P0-2 | 每轮按空槽和资源容量有界批量认领，按组轮询 | 单轮填空槽，不提高 scheduler max_instances，不共享线程间 session |
| P0-3 | 显存准入改为“当前空闲显存 >= 新任务预计增加的显存峰值 + 安全余量”，区分提取与 MIL 推理 | 管理已准入任务的未兑现预留，不重复扣除实际占用；保留 OOM 降级、租约和独占保护 |
| P0-4 | 加入准入拒绝及空槽原因日志 | 能区分无候选、发现受阻、显存不足、独占任务等待、血缘待对账 |
| P1-1 | 缓存已校验模型清单及 artifact 身份 | 完整校验移出频繁控制路径；启动及身份变化时重验，版本固定，禁止永久信任仅路径相同的文件 |
| P1-2 | classify 复用兼容且在用户反馈前产生的两套预测；推理结束后及时释放 GPU 名额 | 同摘要、模型、标签版本、源快照均匹配才能复用；保留预测追溯及实际准确率统计，文件复制不占推理名额 |
| P1-3 | 缩短推理持有训练样本行锁的事务 | 推理在锁外进行、提交前重新按既定全局顺序核验；继续阻止标签变化后激活模型或保存过期预测 |
| P1-4 | 扫描区分快速位置登记和有界身份核验，减少重复配置读取及逐条查询 | 经核验文件可逐批进入队列；只有完整扫描能推断缺失，不能让部分扫描误判删除 |
| P2-1 | 复用同窗口解码音频，减少重复 FFmpeg 启动 | 保持 16kHz、采样时间和特征签名语义，不保存原始音视频片段 |
| P2-2 | 评估持久 worker、模型常驻及更大批推理 | 成本较高，需验证 Windows 进程管理、显存峰值、超时终止和恢复，不作为首轮必要改造 |

推荐第一轮先解决 P0 的队列发现、批量补位和显存准入，再做权重缓存及搬运资源释放。否则即使优化模型推理，任务仍可能在调度层等待。

GPU 共享租约属于公共 `media_lineage`，压缩也使用它。修改准入规则时必须兼容现有独占工作，不应从 video_filter 直接调用压缩业务模块。

`exclusive_train` / `exclusive_compression` 已申请等待时，会暂停它们后面的新共享任务，等待已有任务结束。这是现有公平与互斥策略；当前配置启用了压缩交接，但 runtime.log 未记录当时的租约拒绝理由，**不能确认某个具体空档就是压缩独占造成的**，也不能据此建议取消压缩互斥。

## 6. 下一阶段应补充的运行指标与验收

### 6.1 日志与前端指标

每个控制轮次输出结构化摘要，常规相同状态适当限频：

- 提取、预测、搬运、训练各自的 queued/running 数，新增登记数与跳过已有任务数。
- 配置并发、实际提取并发、GPU 租约数量、待补空槽和最老任务等待时间。
- 拒绝原因：capacity_full、memory_insufficient、exclusive_active、exclusive_waiting、lease_conflict、reconciliation_pending、no_eligible_candidates。
- 显存准入前的 free_mib、estimated_increment_mib、reserve_mib，避免只有“配置 6”看不到实际限制。
- discovery、claim、control_tick、扫描枚举、哈希、DB 锁等待、推理、复制及发布的独立耗时。
- 每个任务区分首次入队、复用已有任务、准入等待、实际开始和最终完成；重复发现不继续打印成“新任务已登记”。

前端应分别显示“视频提取并发”与“其他任务运行数”，避免用 len(_running) 展示为提取并发。

### 6.2 最小验证与预期

后续实施应先用隔离数据库、临时目录和假 worker 验证：

1. 已有 queued 预测因资源等待时，其他预测与提取仍能入队。
2. 单组有 6 个可执行候选且准入允许时，一轮能补齐 6 个；多组轮询不饿死小组。
3. 8GiB 不再被当前公式必然限制为最多 3 个；真正不足时拒绝并说明原因，OOM 可恢复降级。
4. CPU 搬运期间不持有 GPU 推理名额，预测复用不伪造新的事前预测或改变准确率分母。
5. 缓存命中时不重复哈希全部权重；artifact 身份变化、配置变化和异常能触发重验。
6. 扫描拆批后，用户删除、组路径变化、压缩迁移、过期 worker 与摘要完整性仍正确。

功能验证后，再在用户配置组内做短时间性能联调，对比完整摘要吞吐量、平均提取并发、空档时间、GPU/NVDEC 利用率及 CPU/磁盘负载。**不能承诺 6 路一定最快或给出未经实测的倍数提升**；目标是有待处理数据时持续补位，只有可解释的资源或一致性限制才让槽位空闲。
