# video_filter 吞吐与并发调度优化编码计划

> 日期：2026-10-06。需求与证据基线：[research.md](research.md)。本文覆盖原多组改造编码计划。
>
> 状态：P0—P8 代码已落地，最终隔离回归 194 项及压缩回归 38 项通过；改动、迁移、未实测项与部署步骤见 [performance-implementation.md](performance-implementation.md)。此前多组实施记录保留在 [grouped-implementation.md](grouped-implementation.md)，不能作为本次优化已通过的证明。

## 1. 目标与边界

解决已有数据待处理时提取槽位长期空闲、queued 任务阻断发现、单轮补位不足及重复校验/推理造成的效率问题。配置并发上限继续为 6，实际启动数量由剩余显存、任务类型及资源互斥决定。

确定的显存准入条件：

```text
当前空闲显存 >= 新任务预计增加的显存峰值 + 安全余量
```

实现必须同时处理已获准但显存尚未分配的任务预留，防止批量启动时超额准入。不能再将运行任务数乘以固定 2GiB。

贯穿约束：

1. 保持 DINO、VideoMAE、BEATs、eGeMAPSv02，保持 LR/MIL 独立训练、双预测及按 env/组配置选择实际模型；使用本地 GPU，不引入云推理或 ASR。
2. 同一个视频继续使用顺序提取链；多组共享全局容量，调度公平，不为每组单独配置 6 个槽。
3. 只访问当前组允许的目录；liked_source 不执行解码或特征提取，不探索配置外视频及历史旧路径。
4. 完整摘要提交并验证后才能预测，双预测提交后才能自动搬运；保留源版本校验、血缘、稳定期、删除确认、组/代次隔离。
5. 用户删除保留摘要并转为负样本；程序搬运/压缩清源不产生错误负反馈，预测结果不作为训练标签。
6. 每组、每套模型新增 100 个可训练资产才自动重训；首次训练及手动训练沿用现有规则。
7. 保持任务状态、claim token、故障重试边界、现有公共 API 和文件命名；不通过提高 scheduler max_instances 引入控制轮次重叠。
8. 并发任务使用独立 SQLAlchemy session；主服务不加载 CUDA 模型，沿用子进程隔离和进程树终止。
9. 改造公共资源接口须兼容独占训练和压缩；不从 video_filter 导入压缩内部实现。
10. 本轮编码不清理旧数据、不自动迁移生产库、不启动真实服务或执行真实媒体任务。确需持久化变更时生成增量迁移，单独说明部署步骤。

## 4. P1：先补齐调度诊断

目标范围：supervisor、runtime、公共资源模块、worker 日志协议、tracking、prediction/transfer，以及 reporting 和现有 Jinja 页面。

- 每轮记录各组/全局 extract、predict、classify、train 的 queued/running 数，队列容量、新登记/复用/重试数、实际提取并发、最老任务年龄、空槽数及控制耗时。
- 显存准入返回内部诊断：free_mib、pending_reserved_mib、usable_free_mib、estimated_increment_mib、reserve_mib、decision、reason；对外仍兼容 request_lease 返回 lease_id 或 None。
- 拒绝原因固定为 capacity_full、memory_insufficient、exclusive_active、exclusive_waiting、lease_conflict、memory_query_unavailable 等；发现等待另有 reconciliation_pending、no_eligible_candidates。
- 区分首次入队、复用已有任务、资源等待、实际开始和完成。同一 task_id 反复发现不再打印成“新任务登记”。
- 记录 discovery、claim、control_tick、枚举、哈希、锁获取、推理、复制和发布耗时。锁耗时记录本次查询实际等待，不声称等同于完整 PostgreSQL 锁采样。
- 重复的 0/100 重训练等待及相同拒绝原因按状态变化或时间窗口限频；错误仍单独保存全堆栈，关键恢复事件保留。

**验收**：假资源拒绝时能指出空槽原因；页面区分提取并发与其他任务数；日志不包含真实视频名、目录、SQL 参数或凭据。

## 5. P2：增量显存预算与资源准入

### 5.1 配置与预算

由 EnvConfig 唯一解析并同步公开示例配置。建议初始参数如下，单位统一为 MiB；这些是待审查的启动预算，不视为硬件实测保证。

| 建议参数 | 默认值 | 作用 |
| --- | --- | --- |
| VIDEO_FILTER_GPU_EXTRACT_PEAK_MIB | 1024 | 未取得驱动级剖面时，单视频提取的增量预算 |
| VIDEO_FILTER_GPU_PREDICT_PEAK_MIB | 256 | MIL 推理增量预算；结合窗口数/输入规模修正 |
| VIDEO_FILTER_GPU_SAFETY_MIB | 1024 | 每张物理 GPU 的剩余显存保护 |

预算覆盖模型、CUDA 上下文、输入/中间张量和 NVDEC。四路顺序执行采用剩余阶段峰值，包含实际解码/上下文重叠；不相加所有模型。驱动级阶段高水位与 OOM 可提高预算，降低预算只能在有兼容测量且留有余量时进行。提取预算按设备、特征签名、batch_size 和解码/输入规格关联，不将不同 GPU 的测量直接混用。

### 5.2 原子准入与未兑现预留

实现公式为：

```text
未兑现预留 = 已准入任务的剩余峰值预算中，尚未由实际显存占用覆盖的部分
可用于新增准入的空闲 = 驱动报告空闲 - 全部未兑现预留
准入：可用于新增准入的空闲 >= 新任务增量峰值预算 + 安全余量
```

这是用户确定公式的并发实现：实际显存已从驱动空闲值扣除，不重复计费；预留仅覆盖驱动尚未反映的未来增量，包括尚未启动的任务和后续更高峰值阶段。安全余量全局应用一次，不按 active 数倍增。

1. 沿用按物理 GPU 的 PostgreSQL 事务级 advisory lock 和跨进程租约；查询、预算扣减与本次许可登记处于同一短临界区。
2. 同一轮批量准入每个任务都扣减尚未兑现预算，不能六次使用相同空闲快照。
3. worker/管理器通过既有协议报告任务阶段与驱动可归属显存；统计覆盖其 Python 和受管 FFmpeg 子进程，并校验 PID 启动身份。
4. Windows 驱动若无法可靠取得某个 PID 的显存归属，保留该任务未证实兑现的预算，并输出保守估算原因；不能将全 GPU 占用增长随意归属于某个任务，也不能仅凭“进程已启动”清空预留。
5. 内部 telemetry 可缓存一个控制轮次；阶段峰值和未兑现预算仍须在每次准入后更新。
6. 单任务完成/失败/取消后由其持有者释放。进程仍存活或身份不明时保留 conflict；不通过租约心跳超时强行认定 GPU 已释放。
7. 保留独占训练/压缩队列与公平策略；显存查询失败时给出原因并暂缓准入，不绕过保护。

需为 ResourceLease 增加预算和测量元数据，例如 memory_budget_mib、memory_observation（任务类型、阶段、剖面键、可归属占用、采样时间、子进程身份）。旧 active 租约没有测量时按保守兼容预算处理，不删除或重置它们。先核对现有迁移再生成增量迁移，不改写已应用迁移；不把预算仅保存在单进程内存中。

### 5.3 OOM 与容量

- 最大视频提取数继续由 extract_concurrency=6 控制，轻量 MIL 推理全局默认最多 2 个；按共享租约任务类型分别计数，两类合计受统一增量显存预算约束。旧租约类型不明时按提取计数，不简单继续用全部共享租约数抵扣 6 个视频槽。
- 独占训练/压缩继续与全部共享租约互斥；本阶段不改变它们的业务准入条件或为压缩套用轻量推理预算。
- 冷启动估算偏低引发 OOM 时，终止/回收受影响进程树、提升兼容任务预算，并暂时降低提取准入；其他活跃任务不能被误终止。
- 重试次数、任务输入重验及 claim token 终态更新沿用既有语义；不无限重试。
- 稳定成功后可有界恢复有效并发至配置上限，恢复条件及原因可观测；不能永远保留一次 OOM 造成的无说明降级。

**验收**：空闲 5GiB、新任务预算 1GiB、安全余量 1GiB 时显存判定通过，与 active 数无关；批量 6 个冷任务能被未兑现预留约束；真实不足时拒绝；推理/提取并行预算、独占互斥、进程重启及查询失败均有隔离测试。

## 6. P3：模型清单校验缓存

目标范围：[manifest.py](../../automation-server/video_filter/features/manifest.py) 及 runtime/worker 调用方。

- 缓存成功校验的清单、FeatureSignature 和 artifact 身份；键包含清单身份以及各 artifact 的规范路径、文件身份、大小和高精度修改时间。
- 首次使用、任一身份变化、缓存失效时执行完整 SHA-256。校验前后检查身份一致，不发布校验期间变化的结果；错误不写成功缓存。
- 多线程相同清单使用单次并发校验，返回不可共享修改的结果；路径发生变化与外部更新可正确失效。
- 主进程每轮快速身份检查后复用校验结果；独立 worker 对本次固定清单/版本仍保持可信核验，不能把裸“已校验”布尔值作为永久信任。
- 清单/权重应保持只读部署；提供明确强制失效入口及有界周期重验，覆盖元数据保留的字节篡改风险。

**验收**：连续多次控制发现不重复读取全部权重；清单和 artifact 变动、替换、并发访问、校验中变化及 checksum 失败处理正确；不改变 feature_signature 或让已有摘要重提取。

## 7. P4：独立发现与公平批量补位

目标范围：runtime、tasks、supervisor；继续保留 2 秒控制周期和 max_instances=1。

- 训练、已有摘要的预测/分类、新摘要提取分别发现，各阶段都有有界预算。一个 queued/reused/failed 候选不能终止其他阶段。
- 精确按组、代次、目录版本、源快照、标签版本、摘要、模型集与训练配置去重；排除已有同输入 queued/running 候选。旧失败输入维持现有重试规则，不因批量发现变成无限重试。
- 分页/游标越过已有任务与失败候选，避免前 20 条阻挡后续数据。队列只预取足以维持工作槽的有界数量，不将整个视频目录一次展开成任务。
- 提取预取目标初值为全局视频槽数的两倍；各组按轮询分摊总预算，预测/搬运与训练另有小额预算。预算计算在现有数据库任务上进行，不建立第二套任务状态。
- 每轮先回收完成任务，再按剩余提取槽、推理配额及显存预算批量认领；每组每次取一个，循环轮询至没有进展或预算耗尽。
- 领取保留 SKIP LOCKED、claim token 和短提交；长期 worker 使用独立 session。拒绝某候选后继续尝试可执行的其他类型，保持独占队列的先后保护。
- Future 提交失败、关闭时未开始的任务归还队列并释放本次租约；任务开始后进程身份、心跳和回写逻辑保持可恢复。
- 完成事件可标记需要补位，在既有短 tick 中及时回收；本阶段不新增重叠 scheduler 或持续占用终端的控制服务。

**验收**：假 GPU/worker 允许时，一个组的一轮可启动 6 个提取；两个以上组公平分享容量；等待预测不阻止提取入队；满队列下不无限发现；真实空槽能从日志知道原因。

## 8. P5：预测复用与 CPU 搬运分离

目标范围：prediction、transfer、supervisor、worker_client 和 evaluation/reporting 消费者。

### 8.1 复用契约

- classify 入队固定将使用的双模型预测批次及对应 Prediction ID，保持两套输出可追溯。
- 复用必须匹配组/代次、variant、bundle、模型集/模型版本、标签版本、源快照和阈值，且两套预测均已提交；不能只用视频 ID 查最新一条分数。
- 预测模型集包含影子模型，即使实际选择 LR，也不能跳过已活动的 MIL 输出。
- 用户移动、删除或反馈已经发生，或模型/摘要版本已变化时，不将旧分数当成新事前预测；取消/重新发现沿用已有规则。
- 已有合法批次直接用于路由和 TransferOperation，不重新执行推理，也不插入假“新预测”以迎合 task.id。更新 check_gate 对预测批次的检查，保留旧任务快照的兼容路径。
- 无兼容预测时先生成新双预测并提交，再开始搬运；实际准确率按真实产生的预测与用户后续反馈计算，复用不重复扩大分母。

### 8.2 资源阶段与回收

兼容双预测已存在的 classify 走 CPU 搬运配额，不申请 GPU 租约。确需计算时只为推理阶段申请租约，推理提交后释放，再进行源核验、复制、发布和清源。

- supervisor 持续跟踪这个 task 的 Future 与 CPU 搬运状态；GPU 名额释放不表示 task 已完成。
- 释放事件同步 `_running` 中的租约阶段及心跳逻辑，防止对已释放租约继续 heartbeat 导致 resource_lease_lost。
- worker 生命周期、claim token、GPU 授权与资源阶段保持一致；没有许可时不能启动 CUDA worker。
- finally 的再次释放必须幂等；释放后发生文件校验/发布异常仍保留可恢复 TransferOperation。
- CPU 搬运全局默认最多 2 个，避免批量并发复制抢占提取所需磁盘；不能因为不占 GPU 就不限任务数。

**验收**：已有兼容双预测时 classify 不再启动 MIL 子进程；CPU 复制等待时其他提取可准入；用户中途删除/配置变化、同名冲突、阶段释放失败及重启恢复不丢数据；两模型实际准确率与此前相同输入下的结果一致。

## 9. P6：缩短事务与扫描等待

### 9.1 推理和文件 I/O 移出长持锁事务

目标范围：learning、prediction、transfer、feedback，以及共享资源事务。

- 读取并固定模型参数、摘要、输入版本及数值数据，结束读取事务，再进行 GPU 推理。
- 提交前按既有资产 ID 全局顺序、模型 ID 顺序获取短事务锁，并重验全部必要标签/摘要/模型版本；失效则丢弃输出并取消或重新发现。
- 不通过直接删除训练集锁或 require_model 校验来换吞吐；反馈与模型退休必须继续阻止过期结果写入。
- 文件复制和长哈希也尽量在锁外执行，以固定快照和阶段前后校验保证一致；发布及源清理仍严格遵守已经提交的血缘和目标所有权证据。
- 保留 PostgreSQL deadlock/serialization_failure 的有界重试，不在未知提交结果下重复外部文件副作用。

**验收**：假推理/复制阻塞时，互不冲突的短事务可继续执行；标签在推理中改变后输出不能作为有效预测；用隔离 PostgreSQL 验证锁序及并发，SQLite 只能证明状态机功能。

### 9.2 扫描登记拆分与完整性

目标范围：tracking、configuration、supervisor，以及必要的 ScanRun/Observation 元数据。

1. 每轮固定当前组配置与通知代次，先批量取得 Observation/Location 的必要元数据，减少逐文件加载配置和重复查询。
2. 枚举生成受管路径集合；只对稳定、需要身份登记的文件做有界哈希。复用已有位置及元数据一致的哈希规则不变。
3. 哈希在数据库长事务外进行，完成后重验当前组范围及源快照，将已验证的身份分批提交，使已有活动配置下的合法视频可以逐批进入提取队列。
4. 新配置首次基线未建立时，仍须先安全建立该配置的非删除型基线；不能为提速绕过目录版本激活条件或压缩/搬运对账门槛。
5. 整轮扫描在全部观察项核验、血缘消费与通知代次确认前保持 incomplete；部分提交不允许推断用户删除、不推进完整 watermark。
6. 中途文件变化、组路径变化、通知溢出或进程重启时，已核验身份可以保留，但重新扫描并核对当前范围；不可把部分结果当作完整目录快照。
7. 若需增加扫描 checkpoint/phase 字段，在 P0/P2 确认迁移中明确；不使用含原始视频数据的磁盘缓存代替数据库身份记录。
8. 使用 CPU/磁盘有界预算，扫描不能占满用于推理补位的短控制线程；先减少串行查询，再考虑少量身份哈希并行，不盲目开六路全文件读取。

**验收**：初始身份登记不会迫使已确认的其他任务等待全部哈希；部分扫描不产生删除负反馈；组路径切换、同组移动、压缩重编码、用户中途删除和断电恢复均正确。新文件稳定期及 300 秒删除确认期保持原值。

## 10. P7：有界音频复用

目标范围：extraction、media、worker 请求/结果协议及特征契约测试。

- BEATs 已解码的同窗口单声道 16kHz 音频，可供之后的 eGeMAPS 使用；复用键包含源身份、音轨、窗口起止及采样率。
- 保持全视频模态顺序与单线程业务链，不为四路模型增加并行。
- 使用 worker 内有界 RAM 缓存，建议 VIDEO_FILTER_AUDIO_CACHE_MIB=32；6 路上限约额外 192MiB 音频缓存。长视频超过预算时淘汰，后续按原逻辑重解码；不能缓存整个无上限音轨。
- 不将原始音频写盘或写入数据库，任务退出清理缓存；不同视频、源版本、音轨及窗口不能混用。
- 保持 DINO 三个采样时刻、VideoMAE 连续 16 帧、BEATs 分块、eGeMAPS 参数、窗口对齐和缺失掩码不变。
- 不在本阶段改变解码精度、采样位置或输入分布，以免要求旧摘要重新提取；若后续改动产生特征语义变化，必须另行增加 preprocessing_version。

**验收**：预算允许时每个有音轨窗口从 2 次音频解码减少到 1 次，两路结果与原始路径一致；缓存淘汰、短尾、无音轨、多音轨异常及源变化保持正确；记录实际缓存命中与解码耗时，不承诺固定加速倍数。

### 11.2 工作台与性能验收

现有 Flask/Jinja 页面继续沿用，显示 extract_running/configured_concurrency、预测与搬运数、有效显存预算、未兑现预留、队列年龄、最近准入拒绝原因及各阶段耗时。保持只读页面及按组导航，不引入新前端框架。

性能验证先用假任务确认调度能力；真实联调限于用户已配置的组和明确样本，另按用户授权执行，不能由本编码计划自动启动任务或移动视频。

对比 research 基线：提取峰值 3、平均并发 1.392、提取观察空档 159.148 秒；同时记录视频时长/窗口数、完整摘要每小时吞吐、驱动显存、GPU/NVDEC、CPU/磁盘利用率、预测延迟、扫描耗时与失败数。样本不同不能只凭墙钟时间比较加速比。

验收目标：

- 假资源允许且候选充足时，一轮填满配置的提取槽位。
- 真实运行中的空槽均有可解释原因，等待的预测不会阻断其他候选发现。
- 有效显存预算不再随 active 数重复扣除；冷启动与后续高峰有未兑现预留保护。
- 兼容 classify 不重复双预测，复制阶段不持有 GPU 名额。
- 控制路径不反复全量读取权重；完整性、真实反馈和模型准确率统计没有退化。

不以 GPU 利用率瞬间 100% 或始终六路作为唯一验收标准，不承诺未实测的吞吐倍数。出现真实瓶颈时，日志必须说明是显存、独占任务、磁盘、稳定期、对账还是数据不足。
