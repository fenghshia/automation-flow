## 2. 目标、范围与固定行为

系统每 30 秒检查一次配置的源目录，每次最多选择并推进一个顶层源对象，完成安全接管、递归解包、扁平化、图片限容、完整性验证、原子发布和成功后清理。

优先级依次为：原始数据不丢失、成品完整可恢复、禁止覆盖、处理结果确定、图片质量、处理效率。

### 2.1 支持范围

- 顶层目录、顶层压缩包和顶层散落普通文件分别构成独立批次；
- 目录内部可包含任意层级的普通文件和嵌套压缩包；
- 嵌套压缩包递归展开，最终叶子文件统一归入最外层批次；
- 批次内所有目录层级被扁平化，最终只保留文件；
- 静态 JPEG、PNG 超限时使用 Pillow 重编码；
- WebP 和 GIF 不论大小均在校验后逐字节复制，不进行重编码；
- 未超限图片、视频及其他普通文件按字节复制；
- 数据库保存任务状态、稳定性快照、输出摘要及诊断信息；
- 任务私有暂存区支持进程中断恢复。

### 2.2 明确不支持

- 加密、多卷、损坏或资源预算超限的压缩包；
- 超限动画图片（WebP、GIF 除外）以及超限的非 JPEG、PNG、WebP、GIF 图片；
- 符号链接、junction、reparse point、设备文件等特殊文件；
- 已完成源路径的自动增量同步；
- 网络传输、消息通知、图片审核、水印、裁剪或格式转换；
- 自动安装 Pillow 或 7-Zip、自动执行迁移、自动处理真实数据。

任一不支持项或文件处理失败都会使整个批次失败，不发布部分成品。空目录、空压缩包或没有最终叶子文件的批次同样失败。

## 3. 批次与输出映射

源目录只扫描直接子项。一个直接子项就是一个顶层源对象：

| 源对象 | 批次类型 | 输出位置 |
| --- | --- | --- |
| `source/group/` | 目录 | `output/group/` |
| `source/album.zip` | 压缩包 | `output/album/` |
| `source/album.tar.gz` | 压缩包 | `output/album/` |
| `source/pic.jpg` | 散落文件 | `output/pic.jpg` |

复合扩展名整体移除，例如 `.tar.gz`、`.tar.bz2`、`.tar.xz`、`.tar.zst`。不同源对象映射到相同输出根时，后到任务失败；不合并、不覆盖，也不为批次根添加 `D1_`。

嵌套压缩包只作为容器，不进入成品。例如：

```text
outer.zip!/a/inner.7z!/b/pic.jpg
→ output/outer/pic.jpg
```

完整来源链仅用于稳定排序、重名分配和错误诊断。

## 4. 调度、稳定性与生命周期

### 4.1 调度与领取

Scheduler 配置为：

```python
seconds=30
max_instances=1
coalesce=True
misfire_grace_time=120
```

每次触发最多推进一个顶层对象，按以下顺序工作：

1. 恢复一个 `moving`、`processing`、`publishing` 或 `cleanup_pending` 任务；
2. 复查最早的 `waiting_stable` 任务；
3. 原子领取一个 `ready` 任务；
4. 浅层扫描源目录，只登记排序后的第一个未登记对象；
5. 无候选时结束。

稳定性要求为至少间隔 30 秒取得两次一致快照。文件快照包含大小和纳秒修改时间；目录快照基于全部普通文件的规范化相对路径、大小和修改时间生成聚合摘要。快照变化后重新计时；源消失、出现链接或特殊文件时任务失败。

任务领取使用带状态条件的原子数据库更新。单进程重入由 scheduler 参数阻止，多进程并发由 PostgreSQL advisory lock `0x494D47434D505245` 阻止；源路径唯一约束和 `ON CONFLICT DO NOTHING` 防止重复登记。

### 4.2 状态机

```text
首次发现 → waiting_stable ──快照一致且间隔满 30 秒──→ ready
                │                                  ↓
                └────快照变化后重新计时             moving
                                                   ↓
                                              processing
                                                   ↓
                                              publishing
                                                   ↓
                                           cleanup_pending
                                                   ↓
                                               completed

任一确定性错误 → failed
```

| 状态 | 含义 |
| --- | --- |
| `waiting_stable` | 已登记，等待第二次一致快照。 |
| `ready` | 源对象稳定，等待原子领取。 |
| `moving` | 在源目录隔离对象，并校验接管到任务 `pending/`。 |
| `processing` | 解包、收集、命名、压缩并生成暂存成品。 |
| `publishing` | 暂存成品已验证且预期摘要已入库，等待或已执行最终发布。 |
| `cleanup_pending` | 最终成品已发布，等待复验和清理任务暂存数据。 |
| `completed` | 最终成品复验成功，源对象和任务暂存数据已清理。 |
| `failed` | 批次失败；最终路径不被覆盖，并保留系统仍拥有的完整源副本。 |

`completed` 不会自动重新领取。`failed` 默认不会自动重新领取；唯一兼容例外是历史错误精确等于超限 WebP/GIF 不支持错误、任务私有源副本完整、输出名称未被其他活动任务占用且发布尚未开始的记录，这类记录会受控恢复到 `processing`。

### 4.3 源对象接管与恢复

稳定源对象先在源目录内原子重命名为隐藏隔离名称，再跨卷复制到：

```text
automation-server/image_compression/pending/<mission-id>/source
```

复制前可使用 `source.part`，只有逐文件或内容摘要匹配后才转为 `source` 并删除源目录中的隔离对象。不得使用跨卷 `shutil.move()` 代替该过程。

各状态恢复规则：

- `moving`：检查原路径、隐藏隔离路径、`source.part`、`source` 和接管标记，从仍存在的完整副本继续；
- `processing`：保留 `pending/source`，清理并重建本任务的 `unpack/`、`payload/` 和 `result/`；
- `publishing`：最终目标存在时按预期摘要复验；目标不存在而输出卷暂存成品存在时复验并重命名；两者都不存在时失败；两者都存在时只认可匹配的最终目标；
- `cleanup_pending`：先复验最终成品，再删除由 mission ID 精确定位的任务目录；摘要不匹配时不得清理。

整个过程中，完整源数据必须至少存在于原路径、隔离路径或 `pending/source` 之一。

## 5. 压缩包递归与资源限制

支持的扩展名不区分大小写：

```text
.zip .7z .rar
.tar .tar.gz .tgz .tar.bz2 .tbz2 .tar.xz .txz .tar.zst .tzst
.gz .bz2 .xz .zst
```

7-Zip 从配置目录解析 `7z.exe`，使用参数列表调用且不启用 shell；工作目录和解包目录均为任务私有目录。列表、测试和解包的非零退出码均视为失败。解包目标必须是新建空目录，解包后验证所有实际路径仍位于该目录内，并拒绝链接和特殊成员。

递归采用先进先出队列。每项保存暂存路径、来源链和深度；压缩包成员继续入队，其他普通文件加入叶子候选集。所有嵌套层共享一组累计预算：

| 限制 | 上限 |
| --- | --- |
| 嵌套深度 | 16 层 |
| 压缩成员总数 | 100,000 |
| 声明展开总量 | 500 GiB |
| 声明压缩比 | 1,000:1 |
| 磁盘保留空间 | 容量的 5%，且至少 1 GiB |

声明展开大小超过可用预算时在解包前失败。压缩包列表默认超时 120 秒；解包超时按声明大小计算，并限制在 5 分钟至 2 小时。

## 6. 扁平化与文件命名

所有叶子收集完成后统一制定命名计划，按 `(来源链 casefold, 来源链原值)` 确定顺序。目标名比较使用 Unicode NFC 后的 `casefold()`，符合 Windows 不区分大小写的冲突语义。

压缩包成员的 basename 按以下规则规范化：

- 将 Windows 非法字符和控制字符替换为 `_`，移除末尾空格和句点；
- 空名称改为 `_unnamed`，Windows 保留名的 stem 前添加 `_`；
- 保留扩展名，basename 最长 240 个字符，过长时截短 stem；
- 保留合法中文及其他合法 Unicode 字符。

重名使用 `D<number>_` 前缀。每组第一个文件保留原名，后续从 `D1_` 递增；分配前先保留批次中全部原始名称，候选名若撞到原始名称或已分配名称则继续递增。例如：

```text
a/pic.jpg, b/pic.jpg, c/D1_pic.jpg
→ pic.jpg, D2_pic.jpg, D1_pic.jpg
```

不按内容去重。`Pic.jpg` 与 `pic.JPG` 冲突，`pic.jpg` 与 `pic.png` 不冲突。

## 7. 图片与普通文件处理

图片大小阈值固定为 `3 MiB = 3,145,728` 字节，WebP 和 GIF 明确豁免该成品大小上限。扩展名用于初筛，最终格式以 Pillow 解码结果为准；声明为图片但无法完整解码、内容格式与扩展名不匹配或触发 decompression bomb 防护时，整个批次失败。

### 7.1 原样复制

- WebP 和 GIF 不论大小均逐字节复制，保留动画、EXIF、ICC 和其他元数据；
- 其他不超过阈值的图片逐字节复制；
- 视频和普通非图片文件逐字节复制；
- 复制过程计算 SHA-256，并重新读取目标验证；
- APNG、TIFF、BMP、HEIF、AVIF 等仍只有在不超限时才能原样复制。

### 7.2 超限静态图片

- JPEG：固化 EXIF orientation，保留 ICC，移除其他 EXIF；用 progressive、`optimize=True` 在质量 95 至 35 间搜索，必要时以 Lanczos 逐级缩小后重试；
- PNG：依次尝试最高压缩、保留透明通道的 256/128/64 色量化，必要时缩小后重试；
- 不改变文件扩展名，不在格式之间静默转换。

质量下限仍超限时，下一轮尺寸按 `sqrt(target/current) * 0.95` 估算，并确保长宽至少缩小 10%。若无法生成不超过阈值且可完整解码的成品，任务失败。

### 7.3 成品验证

每张成功处理的图片必须满足：存在且为普通文件、Pillow `verify()` 后重新打开可完整 `load()`、格式与扩展名一致、宽高为正。除 WebP/GIF 外，图片实际大小必须不超过阈值；原样复制的文件还必须与源文件摘要一致。

## 8. 完整性、发布与清理

任务暂存结构为：

```text
automation-server/image_compression/pending/<mission-id>/
├─ source
├─ ingest.json
├─ unpack/
├─ payload/
└─ result/
```

`pending/` 是恢复数据且必须被 Git 忽略，不是可通配清理的缓存。所有路径由可信 mission ID 构造。

输出摘要按规范化相对路径排序，将每个文件的相对路径、大小和 SHA-256 汇总后再次计算 SHA-256，同时记录文件数和总字节数。进入 `publishing` 前，预期最终路径、摘要和统计必须在同一个数据库事务中提交。

发布流程：

1. 将完整 `result/` 复制到输出目录直接子项 `.autoflow-image-<mission-id>.part`；
2. 在输出卷重新计算并核对聚合摘要；
3. 目标不存在时，在同一卷内原子重命名为最终路径；
4. 发布后再次验证最终成品并进入 `cleanup_pending`；
5. 再次复验成功后，只删除当前任务的 `pending/<mission-id>/`，随后标记 `completed`。

目录和压缩包批次以目录重命名发布；散落文件使用同卷无覆盖硬链接方式发布。文件系统重命名和数据库提交不是同一事务，因此依赖 `publishing` 状态恢复崩溃窗口。

任何时候都不得直接写最终路径、覆盖或合并已有目标。失败批次不得留下部分可见成品。

## 9. 架构与数据模型

主要模块及职责：

| 模块 | 职责 |
| --- | --- |
| `policy.py` | 扩展名、3 MiB 阈值和资源限制。 |
| `naming.py` | 复合扩展名、Windows 名称规范化和重名分配。 |
| `archive.py` | 7-Zip 调用、隔离解包、递归队列和预算。 |
| `compressor.py` | Pillow 识别、候选压缩、缩放和图片验证。 |
| `manifest.py` | 稳定性快照、内容哈希和输出摘要。 |
| `service.py` | 源接管、单批次编排、暂存、发布、清理和恢复。 |
| `models/mission.py` | `image_compression_mission` 模型和状态常量。 |
| `schedules/process_images.py` | 单任务选择、稳定性复查、原子领取和跨进程锁。 |

本功能不新增 HTTP API。

表 `image_compression_mission` 的字段分为：

- 身份与映射：`id`、唯一 `source_path`、源类型和名称、输出键及其规范化索引；
- 稳定性：源大小、文件数、修改时间、快照摘要、稳定检查次数和复查时间；
- 生命周期：状态、尝试次数、处理开始时间、创建和更新时间；
- 发布恢复：最终路径、输出聚合摘要、文件数和总字节数；
- 诊断：截断后的 `error_message`。

数据库只保存摘要和统计，不保存完整文件清单。输出键使用普通索引而非唯一约束，以便冲突源仍能写入可诊断的失败任务；文件系统无覆盖发布是最终防线。

## 11. 验收与剩余验证

核心验收标准：

- 30 秒调度且单次最多推进一个顶层对象，至少两次间隔 30 秒的一致快照后才接管；
- 目录、压缩包和散落文件按第 3 节映射，嵌套压缩包递归展开且结果扁平化；
- 重名结果稳定，符合 `D1_` 规则，批次根和最终路径均不覆盖；
- 不超过 3 MiB 的图片及普通文件保持字节一致；
- 成功发布的超限 JPEG/PNG 不超过 3,145,728 字节且可完整解码；WebP/GIF 可超过该阈值但必须与源文件字节一致；
- 超限动画（WebP/GIF 除外）、不支持格式、空批次或任一文件失败时，整个批次不发布；
- 两条既有超限 WebP/GIF 格式错误可在源副本完整、最终输出和发布暂存均不存在时逐条恢复；其他 `failed` 记录不自动重试；
- `moving`、`processing`、`publishing`、`cleanup_pending` 中断后均可安全恢复；
- 成功后清理原目录对象和任务 `pending/`，失败时至少保留一份完整源数据；
- 多进程调度不会并行执行两个图片批次；
- 日志和数据库错误可诊断，但不记录凭据、完整配置路径或无限外部工具输出。
